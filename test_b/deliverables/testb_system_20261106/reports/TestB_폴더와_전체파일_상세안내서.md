# Test B 목적과 폴더별 전체 파일 상세 안내서

이 안내서는 `deliverables/testb_system_20261106`을 처음 열어 보는 학습자를 위한 설명이다. Test B가 해결하려는 문제, 이 폴더가 실제로 수행하는 일, 데이터가 계산 결과로 바뀌는 과정, 각 폴더와 파일의 역할을 차례로 설명한다. Python 문법을 몰라도 먼저 전체 흐름과 결과의 의미를 이해할 수 있도록 구성했다.

**이 폴더의 핵심은 이미 준비된 2025년 항적 요약 46,705행·100척에 고정된 계산 규칙을 적용해 시간별 이상점수와 선박별 검토 후보를 재현하는 것이다.** 보고서에는 별도로 수행한 2026년 개발 실험도 소개되어 있다. 따라서 이 폴더에서 직접 실행되는 계산과 보고서가 소개하는 전체 연구의 범위를 구분해야 한다.

확인 기준은 2026년 11월 6일 이 안내서를 추가하기 전의 실제 파일이다. 기존 파일은 **68개, 약 73.47MiB, Markdown 11개**였으며 Python 자동 생성 캐시 6개도 포함한다. 이 안내서와 별도 열람 기록은 기존 68개에 포함하지 않는다. 실제 파일 목록과 읽은 방법은 [파일 열람 기록](TestB_파일열람_기록.json)에 남긴다.

## 1 Test B가 해결하려는 문제

어선이 남긴 항적은 어느 시간대에 어느 해역에서 어떤 모양으로 움직였는지를 보여 준다. 평소와 다른 이동이나 관측 변화가 나타나면 사고와 관련이 있는지 살펴볼 필요가 있다. 사람이 수많은 선박의 모든 시간대를 직접 살피기 어려우므로, 먼저 수치로 검토할 지점을 찾고 그 근거를 제시하는 것이 이 분석의 출발점이다.

대회에는 두 가지 과제가 있다. Test A는 항적을 이용해 자망·통발 등의 **조업형태를 분류**하는 과제다. Test B는 **시간대별 이상점수와 사고시각에 관한 판단**을 다루는 과제다. 이 실행 묶음은 Test B용이며 Test A 분류 모델을 포함하지 않는다. 코드가 만드는 `이동`, `해상정지` 같은 상태명도 자망·통발 정답을 예측한 결과가 아니다.

공지와 보관된 주최 측 답변에서 확인한 Test B의 관심사는 다음 세 가지다.

1. 평상시 항적과 얼마나 다른지 시간대별 점수를 만든다.
2. 사고 전후의 이상징후를 살펴보고 사고로 판단할 선박과 시각을 검토한다.
3. 주최 측이 보유한 사고정보와 제출 결과를 비교한다. 보관된 답변에는 사고시각 오차를 고려한 F1과 6시간 기준이 설명되어 있다.

이 폴더의 실행기는 그중 **점수 계산·검토 후보 선정·계산 근거 제공·재현 확인**을 담당한다. 현재 설정의 사고 판정 임계값은 `null`이다. 100척 모두에 후보 한 개씩을 제공하므로, 후보가 100개 있다는 것은 사고 선박 100척을 찾아냈다는 뜻이 아니다. 공식 제출용 파일을 업로드하거나 실시간 경보를 보내는 프로그램도 아니다.

## 2 먼저 구분해야 할 세 가지 자료 범위

| 구분 | 자료와 규모 | 이 폴더에서 하는 일 | 해석할 때 주의할 점 |
|---|---|---|---|
| 실제 재현 입력 | 2025년 1~6월, 100척, 46,705행 | `src/`가 점수를 재계산하고 저장 결과와 비교 | 이 100척의 공식 사고 정답은 동봉되어 있지 않음 |
| 고정 기준자료 | 기존 2026 Train 계보의 항구 후보·공간 밀도·관측 간격·중심점 거리 | `references/`에서 읽어 비교 기준으로 사용 | 2025년 당시 존재했던 실시간 기준자료라고 볼 수 없음 |
| 개발 연구 | 2026년 잠정 연결 100사건·82척, 후속 전체 선단 7,372척 | `sources/`의 일부 과거 실험 사본과 보고서에서 설명 | 실제 재현 입력 100척과 모집단이 다르고, 후속 연구 전체가 동봉된 것은 아님 |

**100척과 100사건은 서로 다른 숫자다.** 재현 입력은 2025년 선박 100척이고, 개발 실험의 100사건은 2026년 82척에 잠정 연결한 사고 기록이다. 한 선박에 사건이 여러 개일 수 있어 사건 수와 선박 수가 다르다.

또한 계산을 똑같이 재현하는 능력과 실제 사고를 잘 맞히는 능력은 별개다. 저장 점수와 재계산 점수의 차이가 0이어도, 그 점수의 최고 시각이 실제 사고시각과 다를 수 있다. 학습자가 가장 먼저 설명할 수 있어야 할 구분이다.

### 3.2 파일 형식을 읽는 방법

| 확장자 | 뜻과 여는 방법 | 이 폴더에서의 용도 |
|---|---|---|
| `.md` | Markdown 텍스트. Obsidian이나 편집기로 읽음 | 설명, 보고서, 과거 실험 기록 |
| `.py` | Python 소스 코드 | 계산·검증·보고서 생성 |
| `.ps1` | PowerShell 실행 스크립트 | Python 실행 명령을 짧게 감싼 시작 파일 |
| `.csv` | 행과 열을 쉼표로 구분한 표 | 선박 명부, 후보, 사건별 실험 결과 |
| `.parquet` | 열 이름과 자료형을 함께 저장하는 압축 표 | 수만 행의 입력과 시간별 점수 |
| `.json` | 이름과 값을 구조화한 텍스트 | 설정, 출처, 실행 요약 |
| `.jsonl` | 한 줄마다 JSON 한 건 | 시간순 입력을 한 건씩 읽는 가공 예제 |
| `.npy` | NumPy 숫자 배열 | 수백만 개의 공백·거리 기준값 |
| `.ipynb` | 코드·설명·실행 출력이 함께 있는 노트북 | 단계별 학습과 계산 확인 |
| `.png`, `.pdf` | 그림과 페이지 문서 | 시각화, 공지, 결과 보고 |
| `.pyc` | Python이 만든 컴파일 캐시 | 실행 편의를 위한 자동 파일, 학습용 원문은 대응 `.py` |

CSV를 엑셀로 볼 때 선박 식별값은 숫자 연산용 값이 아니라 ID로 읽는다. Parquet와 NPY는 텍스트 편집기로 내용이 보이지 않지만, 이번 확인에서는 형식에 맞는 도구로 실제 내용까지 읽었다.

## 5 루트 파일 다섯 개

### 5.1 README.md

[README.md](../README.md)는 가장 짧은 시작 안내다. 확인한 재현 결과, 설치와 실행 명령, 시스템 구성, 평가 요소와 보고서의 관계, 실시간 적용의 조건, 근거 보존 방식을 설명한다. 처음에는 이 파일로 폴더의 목적을 파악하면 된다.

다만 현재 README에는 초판의 **11쪽 PDF** 설명과 옛 페이지 연결이 남아 있다. 현재 PDF는 **20쪽**이다. 또한 “보고서 원문” 링크가 가리키는 루트의 `핵심 예상 질문 7가지.md`는 존재하지 않는다. `reports/`의 같은 이름 파일도 Test B 원문이 아니다. 현재 자료를 읽을 때에는 이 안내서의 직접 링크와 §16의 문서별 설명을 기준으로 찾으면 된다.

### 5.2 config.json

[config.json](../config.json)은 실행기의 약속을 저장한다. `mode`는 `frozen_baseline_reproduction`, 즉 고정 기준선 재현이다. `training_enabled=false`는 새 학습을 하지 않는다는 뜻이고, `threshold=null`은 사고로 선정할 점수 기준이 정해져 있지 않다는 뜻이다. `external_delivery_enabled=false`는 외부 전송을 하지 않는 설정이다.

메모리 계획은 예상 최대 512MiB와 여유 640MiB다. 실행기는 이 합계인 1,152MiB 이상의 가용 RAM이 있는지 확인한다. 현재 코드는 설정의 숫자를 검사 함수에 전달하는 대신 같은 값의 함수 기본값을 사용하므로, JSON 숫자만 바꾸어 실행 예산을 조정할 수 있다고 이해하면 안 된다. `artifacts`에는 입력·참조·핵심 코드 11개의 SHA-256이 있다. SHA-256은 파일 내용의 지문처럼 사용하는 값으로, 같은 파일인지 비교하는 데 쓴다. 지문이 일치한다고 자료의 사고 정답이나 모델 정확도까지 보증되지는 않는다.

### 5.3 MANIFEST.json

[MANIFEST.json](../MANIFEST.json)은 묶음을 만들 당시의 파일 목록·크기·해시를 보관한다. 설정의 `artifacts`가 계산에 필요한 11개를 검사하는 목록이라면, MANIFEST는 보고서와 그림 등을 포함한 넓은 포장 목록이다.

현재 MANIFEST에는 61개가 기재되어 있다. 그중 58개는 실제 파일과 해시가 일치하고, 2개 문서는 내용이 달라졌으며, 1개 Markdown은 없다. 따라서 “현재 폴더 전체가 MANIFEST와 완전히 일치한다”고 설명하면 안 된다. 세부 차이는 §18에서 정리한다.

### 5.4 requirements.txt

[requirements.txt](../requirements.txt)는 점수 실행에 필요한 네 라이브러리 버전을 고정한다. `numpy==2.2.5`는 숫자 배열 계산, `pandas==2.2.3`는 표 처리, `pyarrow==24.0.0`은 Parquet 읽기·쓰기, `scipy==1.15.3`은 가까운 항구 후보를 찾는 공간 계산에 쓰인다. 같은 버전을 사용하는 이유는 다른 환경에서도 같은 계산 결과를 재현하기 쉽게 하기 위해서다.

### 5.5 run.ps1

[run.ps1](../run.ps1)은 자기 파일이 있는 위치를 기준으로 `src/run_analysis.py`를 찾아 실행하는 짧은 시작 스크립트다. 작업 폴더를 바꾸지는 않는다. `-Output`은 필수 인자이고 상대 출력 경로는 사용자가 명령을 실행한 현재 폴더 기준이므로, 이 안내서의 예시처럼 패키지 루트에서 실행하면 경로가 명확하다. 이 파일에 별도의 점수 공식이 들어 있지는 않다. 실제 계산은 `src/`가 수행한다.

### 7.1 harbors.json

[harbors.json](../references/harbors.json)은 항구로 볼 수 있는 **후보 지점 77개**와 생성 조건을 담는다. 메타데이터에는 0.005도 격자, 최소 선박 수 20, 후보 격자 110개 등이 있다. 코드에서는 현재 시간대 중심점과 가까운 항구 후보 사이의 거리를 구해 상태를 구분한다.

[density.json](../references/density.json)은 어느 공간 격자에 선박 관측이 얼마나 분포했는지를 조회하는 기준이다. `fine`은 0.01도 격자 102,053개, `coarse`는 0.05도 격자 9,174개다. 각 항목은 격자 좌표 두 개와 빈도값으로 구성된다.

코드는 세밀한 격자의 값이 충분하면 그것을 쓰고, 그렇지 않으면 큰 격자를 조회한다. 드문 위치일수록 구역점수의 희소성 항이 커진다. 위경도 격자는 각도 단위이므로 “0.01도는 어디서나 정확히 같은 거리”라고 해석하지 않는다.

### 7.3 gap_reference.npy

[gap_reference.npy](../references/gap_reference.npy)는 기존 자료의 연속 관측 간 시간 차 **3,879,693개**를 담은 `float64` 배열이다. 단위는 시간이며 값의 범위는 1~4,220시간이다. 새로 관측된 시간 차가 기준 분포에서 어느 정도 큰지 환산할 때 쓴다.

저장 배열 자체는 정렬되어 있지 않다. 로딩 과정에서 정렬한 뒤, 현재 값 이하인 참조값 비율을 구한다. 이런 비율 함수를 경험적 누적분포, CDF라고 한다. 기준값 가운데 대부분이 1시간이면 1시간 간격도 큰 누적비율을 갖는다. 따라서 높은 `s_gap`을 곧바로 긴 통신 두절로 읽을 수 없다.

### 7.4 jump_reference.npy

[jump_reference.npy](../references/jump_reference.npy)는 시간순으로 이웃한 두 관측 행의 **기하 중심점 사이 거리 3,879,693개**를 담은 `float64` 배열이다. 관측 간격은 1시간보다 길 수도 있다. 단위는 m이며 범위는 0~약 550,300.78m다. 중심점 거리의 기준 분포에서 현재 거리의 상대적인 크기를 구한다.

파일 이름의 jump는 여기서 중심점 위치 차이를 뜻한다. 배가 실제로 순간이동했다거나 그 거리만큼 정확히 항해했다는 뜻이 아니다. 시간 간격과 기하 집계 방식에 따라 중심점이 크게 달라질 수 있다.

[provenance.json](../references/provenance.json)은 출처와 변환 이력이다. 어떤 원본 Python 파일의 어느 함수·행 범위를 복사했는지, 원본 해시가 무엇인지, 밀도 pickle을 JSON으로 바꾼 이유와 방식, 입력 준비 당시 메모리 확인을 기록한다.

## 8 src 폴더와 점수 계산 원리

### 8.1 frozen_baseline.py

[frozen_baseline.py](../src/frozen_baseline.py)는 점수 계산의 중심이다. frozen은 계산 규칙을 고정했다는 뜻이고, baseline은 개선안을 비교할 기본 방법이라는 뜻이다. 이 파일은 원본 함수와 상수를 복사해 재현 가능하게 만든 것으로, 매 실행마다 새 모델을 학습하지 않는다.

보조 함수는 좌표 사이 거리 계산, 기준 분포에서 순위 비율 구하기, 공간 밀도 조회, 과거 자료 대비 변화량 계산 등을 맡는다. `load_references()`가 기준자료를 읽고, `score_vessel()`이 선박 한 척의 시간순 자료를 계산한다.

#### 상태를 붙이는 규칙

| 상태명 | 코드에서 사용하는 조건의 요지 | 해석 |
|---|---|---|
| `정박정지` | 길이 50m 이하·범위 100m 이하이며 항구 후보 또는 자기 야간 정지 격자에 1km 이내 | 가까운 기준점 부근의 작은 기하 |
| `해상정지` | 같은 작은 기하 조건이며 두 기준에서 모두 2km 이상 | 기준점에서 멀리 떨어진 작은 기하 |
| `연안정지` | 작은 기하이지만 위 두 조건 사이 | 경계 구간의 작은 기하 |
| `이동` | 길이 3,000m 초과, `bbox_m/len_m` 비율 0.6 이상 | 길고 비교적 곧게 나타난 기하 |
| `저속굴곡` | 나머지 경우 | 위 조건에 들지 않는 기하 |

자기 야간 정지 격자는 앞선 자료에서 20~23시·0~3시 정지 조건이 나타난 위치를 누적해 자주 나온 세 곳을 사용한다. 상태명은 편의적인 규칙 이름이다. 특히 `저속굴곡`에 속한다고 실제 속력이 측정되었다거나, `해상정지`가 실제 사고 상태라고 확정된 것은 아니다.

#### 구역점수 s_zone

두 항을 반씩 섞는다. 첫째는 자기 과거 방문 격자에서 얼마나 떨어져 있는가이고, 둘째는 고정 밀도 기준에서 얼마나 드문 위치인가이다.

```text
거리 항 = min(과거 방문 격자까지 거리 / 20km, 1)
희소성 항 = 1 - min(조회한 밀도 / 3, 1)
s_zone = 0.5 × 거리 항 + 0.5 × 희소성 항
```

이미 방문한 격자는 거리 항이 0이다. 첫 관측처럼 방문 이력이 아예 없을 때도 거리 항을 0으로 둔다. 그래서 첫 행의 구역점수는 과거와의 변화보다 고정 밀도에 의해 정해질 수 있다.

#### 변화점수 s_change

앞선 관측이 **24행 이상** 있을 때부터 계산한다. 24행은 반드시 연속된 24시간을 뜻하지 않는다. 빠진 시간이 많으면 실제 달력상으로는 훨씬 긴 기간일 수 있다.

길이와 `bbox_m/len_m` 비율이 자기 과거 중앙값에서 얼마나 벗어났는지 구하고, 현재 상태가 과거에 얼마나 드물었는지도 반영한다. 중앙값에서 벗어난 절대차를 주로 `IQR/1.349`로 나누며, 사분위 범위 IQR이 0이면 표준편차 또는 1을 대체 척도로 쓴다. 얻은 편차 z를 `1-exp(-|z|/2)`로 0~1 범위로 눌러 변환한 값과 상태 희소성을 평균한다. 이는 다른 문서에 나오는 진동 데이터의 MAD 방식과 구분된다.

#### 공백점수 s_gap

직전 관측과 현재 관측의 시간 차, 중심점 거리 두 가지를 각각 참조 분포의 누적비율로 바꿔 평균한다.

```text
s_gap = 0.5 × F_gap(시간 차) + 0.5 × F_jump(중심점 거리)
```

첫 관측은 직전 관측이 없어 계산하지 않는다. 1시간 간격도 계산 대상이다. 예를 들어 연속된 두 시간에 관측이 있어도 중심점이 많이 달라지면 `s_gap`이 커질 수 있다. 이 점수는 통신 상태만을 측정하는 지표가 아니다.

#### 종합점수 score

계산 가능한 성분만 평균한 뒤 최솟값 0.000001, 최댓값 1로 제한한다. 결측 성분을 0으로 바꾸어 평균하지 않는다.

설명용 예로 `s_zone=0.8`, `s_change=결측`, `s_gap=0.6`이면 점수는 `(0.8+0.6)/2=0.7`이다. 이것은 가상 예시이며 실제 사고 확률 70%라는 뜻이 아니다. 성분이 하나뿐인 0.5와 성분 세 개의 평균 0.5는 수치가 같아도 판단에 쓴 정보량이 다르다.

### 8.2 run_analysis.py

[run_analysis.py](../src/run_analysis.py)는 계산 순서를 관리한다. 출력 폴더가 이미 있으면 중단하고, 설정·메모리·해시·입력 구조를 확인한 뒤 선박별 계산을 실행한다. 각 선박의 자료를 시간과 원행 순서에 맞춰 처리하며, 기존 결과와 전수 비교한다.

후보는 선박의 **전체 기간 최고점**이다. 최고점이 여러 개면 `source_ordinal`이 가장 작은 원행을 택한다. 현재 저장 결과에서는 최고점 동점 선박이 0척이지만, 규칙은 코드와 테스트에 보존되어 있다. 후보를 정한 뒤 정확히 3·2·1시간 전 관측이 있으면 그 점수를 설명 자료에 붙인다. 가까운 다른 시각을 대신 채우거나 값을 보간하지 않는다.

새 실행에서 자동 생성하는 파일은 `scored_rows.parquet`, `candidates.csv`, `summary.json` **세 개**다. 기존 `reproduction_001`의 실행 설정·출처 사본 두 개는 보존 작업으로 추가된 기록이므로 새 실행에서도 항상 생기는 파일로 이해하면 안 된다.

### 8.3 src 안의 pyc 두 파일

`src/__pycache__/frozen_baseline.cpython-313.pyc`와 `run_analysis.cpython-313.pyc`는 Python 3.13이 소스 실행 과정에서 만든 캐시다. 별도의 알고리즘이나 학습된 AI 가중치가 아니다. 이해와 수정의 기준은 `.py` 소스다. 이번에는 캐시도 바이트와 코드 객체 메타데이터를 읽었지만 실행하지 않았다.

이 문서는 후속 7,372척 전체 선단 내부 F1 결과를 담고 있지 않다. “공식 허용창 미확인”이나 사고 연결 집단의 국소화를 다음 관문으로 제시한 부분은 작성 당시 상태다. 이후 PDF와 [현재 실행계획](../../../docs/fishing_execution_plan.md)에는 주최 측 6시간 답변과 전체 선단 내부 F1이 반영되었다. 그 후속 결과는 고정 기준 0.75에서 183척 선정, 선박 선정 내부 F1 0.05283, 시각 포함 내부 F1 0.00000이며, 미연결 7,290척을 평가상 음성으로 놓은 가정이 있다. 공식 Test B F1 미확인은 유지하지만, 가정을 밝힌 내부 F1까지 계산할 수 없다고 읽으면 안 된다.

### 17.1 결과만 읽기

Python을 설치하지 않고도 PDF·Markdown·PNG·CSV·JSON을 읽으며 전체 목적과 저장 결과를 이해할 수 있다. 우선 후보표에서 한 선박을 골라 `score`, `component_count`, `prior_observation_count`, `reference1_status`, `reason`을 함께 읽는다. 점수만 보는 습관을 피하는 가장 작은 학습 활동이다.

### 17.2 점수 재현 실행

아래는 패키지 루트에서 실행하는 예시다. 새 출력 이름을 쓰며 기존 결과에 덮어쓰지 않는다. 실제 확인 환경은 기존 기록 기준 Windows·Python 3.13.3·CPU다.

```powershell
Set-Location -LiteralPath 'D:\obsidian\claude\obsidian_export\DATA AI SHIPPING\deliverables\testb_system_20261106'
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe src/run_analysis.py --output results/reproduction_learning_001
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

실행기는 직전 가용 RAM을 확인한다. 부족하면 작업을 보류하고 문서 읽기나 결과 해석을 먼저 한다. 다시 계산하기 직전에 RAM을 다시 확인한다. 사용자 프로그램을 임의 종료하거나 메모리 검사 조건을 낮추어 강행하지 않는다.

성공했다면 새 `summary.json`에서 `parity.all_checks_passed`와 행·후보 개수를 확인한다. 이는 재현 성공의 확인이며 공식 사고 성능 점수가 아니다. 이번 안내서 작성에서는 이 재현 명령을 새로 실행하지 않았다.

패키지 루트의 명령과 작업 위치가 다르다. `support`로 들어가 실행한다.

### 17.4 보고서 재생성과 단순 열람의 차이

완성된 PDF를 여는 데는 보고서 생성 도구가 필요하지 않다. `python reports/build_report.py`는 보고서·그림을 새로 쓰는 명령이며 일부 후속 연구 수치는 코드 본문의 저장값을 사용한다. 새 학습이나 전체 연구 재평가 명령이 아니다. 설명 문서를 읽는 이번 작업에서는 원래 보고서와 그림을 재생성하지 않았다.

| 공백 근거 출력 설명 | PDF는 직전 간격·누락시간을 함께 출력한다고 설명하지만 후보 CSV 36열에는 해당 수치 열이 없음 | 시간별 표에서 별도 계산할 수 있는 정보와 이미 제공된 열을 구분 |
| 복사 문서의 상대 링크 | 원래 폴더 기준 링크가 남아 있어 일부 연결이 끊김 | `sources/copy_manifest.json`에서 원 출처를 확인 |
| 종합검토 Markdown의 갱신 시점 | 후속 전체 선단 연구와 추가 주최 답변 전의 판단이 남아 있음 | 같은 날 작성된 PDF·현재 실행계획과도 갱신 범위를 구분 |
| 노트북과 CLI 차이 | 노트북에는 CLI 메모리 사전 검사·저장 후보 대조 일부가 없음 | 둘의 검증 범위가 동일하다고 설명하지 않음 |

보고서의 내부 연구 수치는 제공된 잠정 연결과 가정 아래의 결과다. 미연결 선박을 평가상 음성으로 둔 것을 실제 미사고 정답으로 바꾸거나, 오차 중앙값이 줄어든 것을 탐지 해상도·조기 탐지 성공이라고 부르지 않는다. 개별 대안이 개선되지 않은 결과도 모든 가능한 개선 방법이 불가능하다는 증명은 아니다.

## 20 이번 열람과 설명 작성의 확인 범위

기존 68개 파일 전체를 대상으로 텍스트 전문, JSON 구조, CSV 전체 행, Parquet 전체 행·열, NPY 전체 값의 범위·유한성·정렬 여부를 읽었다. PNG 8개와 노트북에 포함된 그림 2개를 확인했고 PDF 20쪽의 텍스트를 추출하고 전 페이지를 렌더링해 내용을 살폈다. 캐시 6개는 전체 바이트와 헤더·코드 객체 메타데이터를 읽었다. 파일의 원래 내용은 변경하지 않았다.

이번 확인에서 추가한 것은 이 안내서와 [파일 열람 기록](TestB_파일열람_기록.json)이다. 열람 기록에는 기존 파일의 크기·해시·읽기 방법·표 구조, 메모리 확인과 담당 요청 설정, MANIFEST 대조 결과를 넣었다. 원래의 MANIFEST는 포장 당시 기록으로 남겨 두었다.

2026-11-06 21:49:29 KST 확인한 가용 RAM은 약 3,648.8MiB였다. 추가 작업의 예상 최대 사용량은 600MiB, 별도 여유는 640MiB로 잡았다. 이는 약 77MB의 파일을 한꺼번에 모두 유지하지 않고 표·배열을 차례로 읽고 PDF를 페이지별로 처리한다는 추정에 따른 것이며 실제 프로세스 최대 메모리를 측정한 수치는 아니다. 텍스트 검토를 병렬로 맡긴 작업에도 같은 메모리 규칙을 전달했다.

문서 근거 정리는 Luna xhigh, 코드 검토는 Sol high, 해석 범위 검토는 Astra high로 생성 요청했다. 부모가 안내서의 단일 작성·통합을 담당했다. 이 표기는 에이전트 생성 요청과 도구 응답에 근거하며, 부모 세션의 실행 모델을 바꾸었다는 주장은 아니다.
