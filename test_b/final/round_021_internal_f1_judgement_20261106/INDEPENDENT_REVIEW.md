## 결론과 범위

검토 버전의 내부 F1 계산·사건 매칭에서 실행을 막을 오류를 발견하지 못했다. 실제 전체 선단 결과를 계산하거나 정답 파일을 읽은 검토가 아니므로, 새 TP/FP/FN 및 보고서의 실제 숫자 검산은 실행 후 별도 수행해야 한다.

`counts()`는 선정 수 K와 양성 분모를 보존한다. `policy_results()`는 선박 선정에 연결 선박 수 82, 주 시각 포함 지표에 사건 수 100, 보조 시간 지표에 선박 수 82를 각각 사용한다. 같은 선박의 복수 사건 중 가장 가까운 사건 하나만 ±6시간 이내에서 매칭하고, 동률은 acc_id 문자열 순으로 해소한다. 선박별 예측 하나와 사건 ID 유일성 검사가 있어 사건 중복 TP가 생기지 않는다. 틀린 시각의 예측은 FP, 매칭되지 않은 사건은 FN으로 남는다. 관련 위치: `compute.py:104–151`, `270–285`.

세 정책은 저장된 동일 peak_ts를 사용한다. 정책 예측 CSV와 봉인 기록이 만들어진 후 사건 CSV를 파싱한다(`compute.py:246–270`). 입력 해시 확인 과정에서는 정답 파일 바이트도 읽으므로, 이 순서는 ‘사건 내용 파싱·대조 전 예측 봉인’으로 표현하는 것이 정확하다. 이는 과거 결과를 모르는 독립 검증을 뜻하지 않는다.

## 재현한 문제와 반영 확인

초기 사례 이력 필드는 `ts < peak_ts` 행만 셌다. 합성 행 `ts=[9,10,10], source_ordinal=[1,2,3]`에서 마지막 행이 피크라면 모델의 앞선 행은 2개지만 이 수는 1개였다. 같은 시간의 앞선 행까지 처리하는 기준선의 정확한 24행 이력으로 설명하면 오류다.

수정 버전은 필드를 `observations_strictly_before_candidate_hour`로 명명하고, `exact_scorer_history_count_available=False` 및 같은 시간 선행 행 제외 사유를 저장한다(`compute.py:199–201`). 프로토콜도 정확한 24행 이력 검증으로 쓰지 않는다고 명시했다(`PROTOCOL.md:40`). 보고 경계를 바로잡았으며 점수·선정·F1을 변경하지 않는다.

## 합성 검증 증거

코드를 메모리에서 로드하여 자체 selftest와 독립 추가 조건을 실행했다. 실제 CSV·Parquet는 읽지 않았고, 사례 추출에는 메모리 내 Parquet 대역을 사용해 파일 출력을 가로챘다.

- ±6시간 경계 포함, 7시간 제외, 사건 입력 순서와 무관한 문자열 동률 처리(`10`이 `2`보다 앞섬): 통과.
- 한 선박의 두 사건 중 하나만 TP, 나머지 FN 보존, 미연결 예측 FP 가정, 틀린 시각 FP+FN, 선박/사건 분모 차이: 통과.
- 전부 미선정·입력 부족 사례에서 K=0이어도 사건 분모와 FN 유지, 유보 수 별도 집계: 통과.
- 선형보간 분위수 합성 예제와 같은 시간 이력 누락 재현: 통과.

검증 직전 가용 RAM은 4,324.6 MiB, 합성 작업 예상 최대는 64 MiB였다. 확인된 Python 프로세스는 검증 프로세스 23.0 MiB였다. 대형 로딩·점수화·학습·반복 RAM polling은 수행하지 않았다.
