# Round019 라벨 없는 전 선단 점수 계산 근거

2026-11-06 14:46:54 KST에 **7,372척·3,887,065행**의 동결 점수 계산을 완료했다. `execution_001/score_metadata.json`의 상태는 `complete`, 단계는 `finished`다. 전체 3,887,065개 점수가 유한하며 선박 오류·유한 점수가 없는 선박·비정상 중심점 행은 모두 0이다. 사고 라벨 결합과 성능 평가는 별도 담당자가 수행한다.

## 입력·점수 계약

- 입력은 `../round_017_fleet_negatives_20261106/execution_001/hourly_01.parquet`부터 `hourly_06.parquet`까지 6개 요약 파일로 제한했다. 원자료·라벨·신원 재식별 경로를 읽지 않았다.
- 모든 입력 시각을 검사했다. 정수 epoch hour의 최솟값은 490896, 최댓값은 495239이며, 전부 2026년 1월 1일 이상·7월 1일 미만이다.
- `deliverables/testb_system_20261106/src/frozen_baseline.py`의 `load_references`와 `score_vessel`을 수정 없이 호출했다. 저장 참조도 변경하지 않았다. 모델 학습·새 임계값 적합은 하지 않았다.
- 한 선박의 전체 행을 모아 `ts`, `rfid_time`, `source_ordinal` 순으로 안정 정렬했다. `rfid_time = ts % 24`이며 최고점 동률은 점수 내림차순·원행번호 오름차순으로 선택한다.
- 원행과 선박을 제외하지 않는다. 일반 오류 경로는 별도 `vessel_errors.jsonl`과 결측 요약으로 보존하며, 오류가 있으면 완료 상태를 `complete_with_vessel_errors`로 구분한다. 이번 실행의 오류는 0이다.

출력 `execution_001/vessel_peaks.csv`의 열은 다음과 같다.

```text
rfid_id,n_rows,peak_score,peak_ts,peak_state,median_score,p95_score,n_unique_hours,gap_total_h,activity_radius_km,n_finite_scores
```

`gap_total_h`는 중복을 제거하고 정렬한 시각 차이에 대해 `sum(max(diff - 1, 0))`으로 계산한 내부 미관측 시간이다. 관측 시작 전·종료 후 시간은 포함하지 않는다. `activity_radius_km`는 경도 중앙값·위도 중앙값으로부터 시간별 요약 중심점까지의 최대 haversine 거리다. 실제 GPS 항적·속력·침로로 해석하지 않는다.

## 적재·복구와 자원

입력을 65,536행 이하 Arrow 배치로 읽어 RFID 문자열의 CRC32를 128로 나눈 값에 따라 디스크로 분할했다. 선박 이력을 나누어 점수를 계산하지 않는다. 적재 방식만 바꾸고 한 선박의 이력을 유지한다. 모든 원행·선박 수와 분할 해시를 `staging_manifest.json`에 기록했다. 선박별 결과는 JSONL에 쓰고 매번 flush·fsync하여 체크포인트로 남겼다.

초기 순차 실행은 14:26:05 KST, 가용 RAM 4,050.70 MiB에서 시작했다. 프로세스 peak 1 GiB 추정과 여유 640 MiB를 사용했다. 827척·443,227행의 유한 점수를 저장한 뒤 총괄이 병렬 실행을 명시 요청했다. 14:32:19 KST에 해당 작업의 PID 1708만 종료하고 원래 코드를 그대로 둔 별도 `score_fleet_parallel.py`로 전환했다. 기존 체크포인트는 모두 보존했다.

병렬 직전 가용 RAM 3,490.79 MiB·논리 CPU 16개를 확인했다. 부모 512 MiB + 작업 4개 × 512 MiB + 여유 640 MiB = **3,200 MiB** 예산을 적용했다. 각 작업은 서로 다른 분할 번호의 modulo 4 구간과 별도 체크포인트 파일을 소유했다. 최종 부모가 중복 선박이 없음을 검사하고 합쳤다.

작업별 관측 프로세스 peak는 **278.133–278.746 MiB**였다. 개별 peak 합 1,113.714 MiB는 동시 합산 peak 실측이 아니다. 변경하지 않은 순차 helper의 단계별 RAM 사전 검사는 여전히 프로세스 peak 1 GiB·여유 640 MiB라는 더 보수적인 가용량 관문을 사용한다. 512 MiB 예산이나 1 GiB 관문은 운영체제의 강제 메모리 상한이 아니다. RAM 반복 감시 루프는 만들지 않았고 단계 전환 시에 확인했다.

병렬 실행은 874.972초, 최초 실행부터 완료까지는 1,249.298초였다. 모든 원본·병렬 작업·통합 프로세스가 종료됐음을 완료 감사에서 확인했다.

## 재사용 시의 제한

이번 병렬 helper 자체에는 동시 부모 프로세스 잠금과 초기 오류 체크포인트 전파를 일반화한 기능이 없다. **이번 실행에서는** 외부 확인으로 원래 PID 종료, 부모 1개, 작업 4개, 원래 오류 기록 0, 초기 827척 모두 유한 점수를 확인했다. `execution_001/parallel_runtime_guard.json`에 확인 시각과 조건을 기록했으며 최종 감사에서도 검증했다. 이는 이번 실행을 검증한 것이며 일반적인 동시 실행 내성을 입증하지 않는다.

현재 산출물은 완료됐으므로 재실행할 필요가 없다. 향후 장애 복구가 필요하면 이전에 생성한 모든 작업 프로세스가 종료됐음을 먼저 확인하고 **같은 작업 수 4개**를 유지해야 한다. 작업 수를 바꾸려면 새 실행 폴더 또는 명시적 체크포인트 소유권 재분배가 필요하다. 동시에 여러 부모를 실행하지 않는다. 원래 순차 실행의 `score_run.lock`은 전환으로 남은 PID 1708의 기록이며 실제 실행 중이라는 뜻이 아니다.

점수 재현·적재 보존의 기술 검증과 사고 판별 성능은 구분한다. 이 단계는 라벨을 읽거나 성능 결과를 계산하지 않았다. 실시간 탐지·공식 F1·물리 장치 동작을 검증했다고 주장하지 않는다. 학습자가 설명할 질문은 “선박의 이력을 유지한 적재 분할과 이력을 잘라 점수를 바꾸는 연산 분할은 왜 다른가?”, “개별 프로세스 peak의 합을 실제 동시 peak라고 부를 수 있는가?”이다.
