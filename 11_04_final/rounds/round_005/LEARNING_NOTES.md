# Round 005 학습 기록

이 문서는 본인 학습자용이다. 아래 시스템 산출 검증과 학습자의 설명 능력은 별개이며, 학습자의 이해를 직접 평가하지 않았다. 하드웨어·센서 실험은 없다.

이번 흐름은 읽기 전용 개발 NPZ 및 ID manifest → fold0 역할·멤버십·순서 검사 → FIT 중앙값 대치와 원결측 표시 → float32 312열 입력 → pretrained TabICL 문맥 바인딩 → 고정 두 질의의 원확률 비교다. 원자료에서 새 물리량을 추출하거나 시각 없는 좌표로 속력·가속도를 만들지 않는다.

기술 목표는 원래 순서의 입력 복구와 작은 원출력 재현 검사다. 학습 목표는 집합 해시와 순서 해시, 문맥 fit과 계수학습, 수치 재현과 F1 평가, 합성 smoke와 실제 입력 자원비용을 구별하는 것이다.

예상: 동일 개발 입력·문맥 순서·체크포인트를 사용하면 CPU의 두 질의 출력이 저장된 CUDA 확률과 허용오차 1e-4 이내일 수 있다. 이는 검증할 가설이며 보장값이 아니다. 입력 단계의 실제 결과는 export와 독립검산 모두 통과이며, 모델 단계의 최종 관찰은 ROUND_REPORT를 따른다.

조건: FIT3144, INNER787 중 원순서 앞2개, seed42, estimators8, batch1, threads3, CPU/FP32. 모델 실행은 최대1회/600초, 직전 가용RAM≥3GiB, 실행 중1.5GiB 미만이면 소유 프로세스만 중단한다. batch1은 질의수가 아니라 ensemble-view 묶음이라는 점을 구별한다.

관찰: membership hash는 같은 선박 집합을 증명하지만 행순서를 증명하지 않는다. 실제 원순서 배열의 hash는 roster 순서의 hash와 다를 수 있다. 배열의 값과 순열을 분리하여 판단한다. 첫156열의 결측 여부를 뒤156열로 추가하므로 최종 입력은312열이다. 이 입력 복구는 보호된 과거 전체7372행 특징을 모두 재생성했다는 뜻은 아니다.

설명 질문:

1. 같은 선박 집합 해시를 가진 두 배열의 예측이 왜 다를 수 있는가?
2. 왜 model.fit에 FIT 라벨은 전달하면서 INNER 라벨은 전달하지 않는가?
3. 2척 원확률이 일치하더라도 왜 micro-F1 0.7이나 일반화 성능을 주장할 수 없는가?
4. 왜 16행 합성 smoke의 시간과 메모리를3144행 실험으로 단순 외삽하면 안 되는가?
5. 입력 검사가 성공했는데 실행이 막힐 때, 원자료·계약·전처리·모델·자원 계층 중 어디서 실패했는지 어떤 기록으로 구별하는가?

계약 계층의 오류는 ordered JSON digest와 frozen membership digest를 혼동한 것이었다. 실행 전에 근거가 확인된 단일 직렬화 공식으로 정정했다. 값이 맞을 때까지 여러 정렬을 시도한 모델 선택 실험이 아니다. 소스 동결 과정에서는 stdout 문구 수정 때문에 승인 해시와 실행 해시가 달랐다. 원본 승인 기록을 보존하고 소스 사본·역변환 해시로 정확한 차이를 확인했다.
