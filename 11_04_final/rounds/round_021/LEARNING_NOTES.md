# Round021 학습 기록

본인 학습자용이며 선수지식·학습시간·이해 수준은 아직 평가하지 않았다. 실제 데이터 기반 코드 실행과 검산을 다루며 하드웨어 실험은 없다.

1. **입력 계약**: 하나의 선박 ID가 세 모델에서 같은 fold와 역할, 정답, 관측일수를 가리켜야 한다. INNER787은 ES393과 SELECT394로 나뉜다. ID 집합 일치 후 순서도 맞춰야 한다. 라벨 순서만 비교하면 같은 라벨을 가진 두 선박의 확률 교환을 발견하지 못할 수 있다.
2. **확률 결합**: 이미 저장된 세 모델 확률의 로그12열을 사용한다. meta모델과 scaler는 SELECT에만 적합한다. SELECT에서 측정한 적합도는 in-sample이며 성능 근거로 OUTER 점수를 대체하지 않는다.
3. **공간 참조**: 좌표 셀의 체류 분포를 선박별 정규화하고 FIT 선박을 같은 가중치로 평균해 클래스 prototype을 만든다. Bhat 계수는 두 분포의 겹침을 나타내며 속도·가속도 또는 조업구간 정답이 아니다. query의 정답을 prototype 계산에 사용하지 않는다.
4. **보호와 개선**: micro는 전체 맞힌 척수/5897이다. 보호 TP가 같더라도 기존 정답 선박을 잃고 다른 선박을 맞혔을 수 있어 gain/loss를 함께 확인한다. 자망·통발 recall 상승만으로 개선을 결론짓지 않고 precision/F1와 FP 출처를 본다.
5. **증거 수준**: 개발 OUTER는 반복 노출됐고 새로운 독립 평가가 아니다. 입력의 코호트 연도와 행별 관측연도, 요청 모델과 호스트 실행 메타데이터, 메모리 예상값과 실행 중 관찰값을 구분한다.

설명 과제: (a) INNER 전체 검증과 SELECT 추출을 분리한 이유를 본인의 말로 설명한다. (b) query가 FIT prototype에 들어가는 누수 사례를 그려본다. (c) micro가 오르지만 TP3가91이면 이번 조건에서 어떤 결정을 내려야 하는지 계산한다. (d) profile 누락을 제외하지 않고0으로 대치할 때 무엇을 별도로 관찰해야 하는지 설명한다.

기술 구현·검산의 실제 결과는 ROUND_REPORT.md와 실행 산출물을 따른다. 위 질문에 대한 학습자의 답변은 아직 받지 않았으므로 이해 달성을 평가하지 않는다.
