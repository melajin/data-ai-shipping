# Round024 independent source review

## Decision and scope

Approved the frozen source set for one preregistered S1 FIT-only internal 4-fold diagnostic: 3,144 FIT rows, seed 42, four folds, baseline/candidate paired fits (eight total), and the fixed gate `candidate >= 1,833 AND candidate - matched baseline >= 16`. This approval covers the listed round024 source files and prepared caches only. It does not authorize a full 3-fold run, S2, retries, tuning, raw-data rescans, holdout/Test evaluation, or an official-score claim.

Reviewed `AGENTS.md`, `NEXT_SESSION.md`, round024 `ROUND_PLAN.md`, `MODEL_SWITCH_HANDOFF.md`, `MANAGER_ACTIONS.md`, `copied_inputs.json`, `runtime_contract.json`, `experiment.json`, the launch/freeze scripts, the review scripts, the T5/S1 cache manifests and count-equivalence summary, the round023 report's source-boundary note, and `supplement_metrics.py`. I read the source code and metadata only. I did not run `prepare_round024.py`, training, freeze, `verify_gate_result.py`, `reinfer_saved.py`, or metric calculations; I did not open the original NPZ, raw source data, prepared cache contents, or any holdout/Test row.

## Findings

- Setup provenance: all 14 `copied_sha256_before_low_memory_patch` entries matched their round023 source hashes when checked. Round024 patch hashes matched the setup record except `manager/launch.py`, which has the documented post-setup manager changes. The author later changed `code/run_gate.py` and `code/s1_features.py`; `MANAGER_ACTIONS.md` distinguishes setup hashes from final approval hashes. The approval JSON records the current file hashes.
- T5 metadata records a 2026 FIT query scope, no labels used, zero Test2025 query rows materialized, and no retained individual Test outputs. It explicitly says Test2025 geometry was read only for the previously approved shared-harbor aggregate. Count equivalence to the legacy `log1p` measure is within `8.9e-16`; pointwise mask equivalence is explicitly false/unverified, so the review does not claim it.
- S1 metadata binds the cache to the ordered 3,144-vessel FIT roster and the predicate `year == 2026 AND id IN exact fold0 FIT roster`. The recorded scanner output has zero returned year/ID mismatches. Physical row-group decoding of unmatched rows was not measured. The feature remains a record/time-bin centroid proxy, not dwell time or complete geometry occupancy.
- Static code review found the label-use boundary intact: T5 rebuilds per CV training fold; FIT self-contributions are excluded from cell and global prior calculations; S1 receives fold training indices/labels and no validation labels. Code-author changes construct the candidate matrix after baseline persistence, release the base matrix before candidate fitting, and release the final monthly temporary dictionary after copying its values into the result arrays. No feature definition, split, estimator setting, or threshold changed in those edits.
- `verify_gate_result.py` recomputes saved aggregate and fold metrics, checks FIT partition/evidence shapes and cache provenance, model hashes, class order and feature count, and guards the result scope. Reviewer changes require the exact round024 gate path and validate every approved round024 source hash before checking outputs.
- `reinfer_saved.py` reloads models one at a time and compares each fold's probabilities (absolute difference at most `1e-7`) and argmax against saved FIT predictions. Reviewer changes bind the source NPZ bytes to `gate_result.input_hashes.fold0_features_npz`, require the exact FIT row/label order and exactly eight unique fold/variant records, and constrain model paths to round024. The prior report states the source NPZ contains the 5,897-row development roster and no holdout/Test rows; this review did not open it. The script materializes that development archive before selecting FIT rows, which is a known peak-memory limitation; the manager launcher measures the complete process family and applies the configured RSS and available-RAM stops.
- `supplement_metrics.py` is a saved-output diagnostic, not a training or selection path. It validates the same source NPZ hash and ordered FIT roster, uses saved FIT predictions plus FIT observation-day metadata, emits aggregate paired/class diagnostics and a seeded within-roster bootstrap, and marks the result diagnostic rather than independent or official evaluation. It was not run.
- `launch.py` checks the frozen approval hashes before every child start, blocks concurrent Python computation (excluding only the verified identical-argv Windows venv bootstrap parent), sets one-thread environment variables, uses below-normal priority, checks entry/stage RAM, samples owned process-family RSS, enforces the 0.75 GiB RSS cap and 0.5 GiB emergency free-RAM floor, and preserves the fixed deadline and one-job limits. The 0.5 GiB expected peak is an estimate, not measured evidence. The manager's 03:04:06 UTC bootstrap preflight is recorded as launcher evidence, not a parallel training job.

## Verification evidence and limits

The manager recorded `ast.parse` success for all nine production, review, manager, and supplement Python files without importing project modules or reading data (`manager/syntax_check.json`). Static review cannot establish runtime correctness, probability agreement, actual peak RSS, or gate performance. Those remain unmeasured until the manager's sequential supervised launch and post-run checks.

No holdout/Test data were opened for this review. The inherited cache manifest documents its pre-existing unlabeled shared-harbor Test2025 aggregate. No new Test/holdout access is authorized by this approval. The gate's outcome and any later deployment/official score remain unknown.

Final approved hashes are in `gate_approved_sources.json`. The launcher requires the resulting `snapshot_s1_gate/freeze.json` and rechecks those hashes before a computation starts. This review authorizes that freeze/one gate attempt under the stated contract; it does not assert that either action has already occurred.
