## 3. 성공 기준을 먼저 고정한다

현재 사용자는 특정 F1·오탐률·시간오차 수치를 지정하지 않았다. 감독자는 데이터와 평가 가능 범위를 확인한 첫 round에서 `SUCCESS_CRITERIA.md`를 작성한다. 임의의 숫자를 사용자가 정한 목표처럼 쓰지 않는다.

성공 기준에는 최소한 다음을 포함한다.

1. **입력·정답 근거:** 입력 버전과 역할이 확정되고, 평가에 사용하는 사건–선박 연결 신뢰도가 명시된다. 근접 단일 후보나 사고 미등재를 각각 확정 양성·음성으로 자동 사용하지 않는다.
2. **독립 평가:** 규칙·임계값·전처리를 정한 자료와 결과 확인 자료를 분리한다. 같은 사건·관련 선박이 두 역할을 겸하지 않게 한다. 반복해서 본 OUTER를 새 독립 검증이라고 부르지 않는다.
3. **성능 판정:** 기존 동결 기준선과 동일한 사건·기간·가용정보로 놓침·오탐·시각오차를 비교한다. 사전 고정한 채택 기준, 악화 허용 여부, 표본 불확실성·검정/구간을 기록한다. 근거 부족 시 성능 목표 충족을 선언하지 않는다.
4. **출력 완결성:** 사고/미사고/자료부족을 내부에서 분리하고 제출 공란·시각·점수·ID 형식과 근거를 검산한다.
5. **재현성:** 코드·입력·환경·로그·실제 종료코드·독립 검산을 확보한다.

공식 시간오차 F1 수식이 없으면 내부 지표의 이름과 한계를 표시한다. 내부 개선 확인과 공식 대회 성능 인증을 같은 성공으로 취급하지 않는다. 첫 round에서 정의한 성능 기준을 충족하지 못했다는 이유로 뒤에서 낮추지 않는다. 정당한 범위 변경은 변경 이유·시점·이전 결과 노출 여부를 기록하고 새 비교로 분리한다.

## 4. round 실행 절차

1. `STATUS.json`의 소유 감독과 최신 성공 기준·다음 지시를 읽는다.
2. 입력 버전·이전 결과·남은 의문을 확인한다. 새 ZIP 입력이면 호환성을 먼저 검사한다.
3. `ROUND_PLAN.md`에 이번 검증 질문, 예상 결과, 변경 항목, 고정 항목, 판단 기준, 예산·종료 분기를 실행 전에 적는다.
4. 독립 작업을 실제 Orca Luna xhigh 세션에 위임한다. 같은 파일을 쓰는 작업은 병렬화하지 않는다.
5. 실행자는 결과·실제 종료코드·근거·실패를 감독자에게 보고한다. 감독자는 `worker_done`·질문·에스컬레이션을 처리한다.
6. 독립 검산 뒤 이전 기준선과 현재 결과를 같은 조건에서 비교한다. 입력 버전이 다르면 직접 차이를 성능 향상이라고 해석하지 않는다.
7. `ROUND_REPORT.md`, `NEXT_ROUND.md`, `LEDGER.md`, `STATUS.json`, `NEXT_SESSION.md`를 갱신한다.
8. 성공 기준을 충족하면 근거와 완료 범위를 보고하고 자동 후속 실행을 종료한다. 미충족이며 유효한 다음 가설이 있으면 새 감독 세션으로 인계한다.

## 5. 매 round 보고서 필수 항목

- 이번 질문과 기술 목표, 결과를 이해하기 위한 핵심 설명 질문.
- 입력 버전·대상·분할·조건·예상 결과.
- 실제 실행·실패·수정·검산 결과와 원본 경로.
- **이전 round와의 비교:** 개선·악화·동일·비교 불가를 구분. 분모·지표·정답 수준을 일치시킨다.
- **현재 round 결과:** 측정값, 의미, 미확인 사항, 채택/보류/기각 이유.
- 성공 기준의 항목별 충족 여부와 남은 차이.
- **다음 round 검증:** 하나 또는 소수의 구체적 가설, 필요한 근거, 변경할 것과 고정할 것, 종료 기준.
- 다음 세션이 읽을 파일·실행 명령·소유권·이미 한 작업.

보고서를 작성했다는 것만으로 round의 계산이 완료되거나 성공 기준이 충족된 것은 아니다. 실패 로그와 반증된 가설도 이력에 보존한다.

## 6. 다음 감독 세션으로 실제 인계

round 말미의 감독자가 Orca CLI로 **새 GPT-6.1 Sol high 세션**을 생성하고 `NEXT_SESSION.md`와 해당 round의 인계 지시를 전달한다. 새 세션은 Luna xhigh 실행/검산 구조를 그대로 유지한다.

인계 증거로 다음을 남긴다.

- 이전·다음 round 번호와 소유 감독 session ID.
- 정확한 모델·effort 요청, launch operation ID, 반환 handle.
- 프롬프트 전달 결과(`journaled`, `handed-to-terminal` 또는 메시지 수락 영수증).
- 새 감독의 인수 ACK와 원본 결과 경로.

프롬프트 전달이 확인되면 이전 감독은 새 계산을 중복 시작하지 않는다. 새 감독은 `STATUS.json`의 자신을 향한 인계 정보와 소유권을 확인하고 ACK한 뒤 round를 시작한다. 인계 중 상태는 `handoff_pending`, 인수 뒤에는 `running`처럼 실제 상태에 맞춰 기록한다. 기존 작업자가 남았다면 종료 보고 또는 명시적인 관리권 인계를 먼저 처리한다.

세션 생성 실패·결과 불명확 시 재차 새 세션을 만들지 않는다. Orca의 operation ID와 recovery 절차를 따른다. 단순한 침묵·timeout으로 이전 세션 종료나 소유권 회수를 추정하지 않는다.

## 7. 지속 수행의 의미와 실제 장애

사용자는 성공 조건 충족까지 계속 진행하도록 승인했다. 따라서 일상적인 다음 round마다 다시 실행 허락을 묻지 않는다. 데이터 확인·국소 수정·재현·새 가설 검증 등 가능한 진전은 계속한다.

다만 같은 설정을 근거 없이 반복하거나, 성공 기준을 바꾸거나, 정답을 만들어 무한히 돌리지 않는다. 외부 식별정보·정상 정답·규정 해석 등 없으면 어떤 실험으로도 해결되지 않는 조건은 `blocked_external_evidence`로 구체적으로 기록하고 필요한 정보와 이미 시도한 경로를 보고한다. 근거 없이 성공·실행 중을 표시하지 않는다.

실행 중인 컴퓨터/Orca가 종료되면 지속 실행이 보장되는 것은 아니다. 상태·인계 파일로 재개할 수 있게 한다. 예약 작업·watch loop를 따로 만들지 않으며 Orca의 실제 worker 알림과 세션 인계를 사용한다.

## 8. 새 입력 1103_v2의 우선 처리

입력 ZIP: `C:/Users/dlehs/Downloads/문제 데이터_수정_1103_v2.zip`.

`intake/1103_v2/`의 검사 결과를 읽고 감독자가 round_001의 입력 호환성 게이트를 처리한다. ZIP 파일명이 새롭다는 이유만으로 사고정보·ID·기간이 바뀌었다고 가정하지 않는다. 작은 XLSX가 동일해도 큰 CSV의 내용 동일성을 증명하지는 않는다.

새 데이터가 바뀌었다면 기존 캐시의 유효성을 파일별로 판정하고 영향받는 처리만 재계산한다. 새 입력의 검증 없이 예전 캐시를 새 버전 결과라고 부르지 않는다. 전체 압축 해제는 필요한 공간·경로·중복 비용을 확인한 뒤 별도 새 폴더에 수행하며 원본을 덮어쓰지 않는다.

## 9. RAM 부족 시 작업 순서 변경 — 사용자 추가 지시

메모리 작업 전 가용 RAM과 예상 최대 사용량·병행 작업을 확인한다. 부족하면 먼저 가능한 다른 작업을 수행하고, 보류했던 작업의 실행 직전에 RAM을 다시 확인한다. 이전 스냅샷이나 시간 경과를 재확인으로 대신하지 않는다. 청크·스트리밍·순차 실행과 병렬 수 축소를 우선하며 사용자 프로세스를 임의 종료하지 않는다. 이 규칙은 모든 worker 및 다음 감독 세션에 적용하고, 반복 메모리 polling/watch 대신 실제 작업 단계에서 확인·기록한다.
