# 11_04_final round_001–round_020

괄호 안 원본 경로는 DATA AI SHIPPING/ 저장소 루트 기준이다.

이 문서는 각 회차의 질문, 평가 모집단·단계, 실제 결과, 채택 여부, 이전 회차와의 변화 및 다음 회차에 미친 영향을 원문 보고서 기준으로 정리한다. 시스템·실행기 검증 회차는 분류 성능이 아닌 해당 검사의 관찰값으로 표시한다. (원본: 11_04_final/AGENTS.md; 11_04_final/CYCLE_PROTOCOL.md)

## round_001 — T5 입력 정밀도와 고정 기준선 재현

기존 X304 내 T5가 CSV 파서 변환을 거치면 바뀌는지, 현재 모델 확률과 예측에도 영향이 있는지 진단했다. 개발 5,897척의 3-fold 기존 FIT/INNER/OUTER 역할을 유지해 저장된 LightGBM 5seed 15개를 입력 두 방식으로 추론했으며, 새 모델 학습은 없었다. 기본 parser 입력에서 기준선은 3,497/5,897, micro-F1 0.5930133966, macro-F1 0.5252719739였고, round_trip 입력도 점수·argmax·정답 수가 같았으나 확률 변화 최대는 OUTER 평균 기준 0.0012018579였다. 기본 NPZ T5를 고정 입력으로 유지했고 원 동적 T5 배열 대조와 과거 .59183 원인 설명은 미측정으로 남겼다. 이 재현 관문 이후 새 모델 비교인 round_002로 이어졌다. (원본: 11_04_final/rounds/round_001/ROUND_REPORT.md)

## round_002 — CatBoost 및 선택 결합

다른 모델이 같은 X304와 FIT를 학습해 오류를 줄일 수 있는지 비교했다. 개발 OUTER 5,897척에서 LightGBM seed42 재학습은 3,476척, micro-F1 0.589452; CatBoost는 3,424척, 0.580634; INNER_SELECT로 고른 결합은 3,474척, 0.589113이었다. CatBoost와 결합은 사전 기준 micro 개선 및 통발 recall 보호를 충족하지 못해 둘 다 채택하지 않았다. 이전 기준선을 새로운 ES 분리 조건에서 재학습했기 때문에 round_001의 .593013과 이번 .589452 차이를 새 후보 효과로 취급하지 않았다. 회차 완료 뒤 일시정지했으며, 이후 기록상 사용자가 명시 재개한 뒤 round_003 분석이 진행됐다. (원본: 11_04_final/rounds/round_002/ROUND_REPORT.md; 11_04_final/USER_PAUSE.md)

## round_003 — TabICL 저장 확률의 판정 손익

저장 확률을 다시 학습하지 않고 기존 통발 배수와 INNER micro 선택 배수의 효과를 분리해 계산했다. 각 seed의 개발 OUTER 5,897척에서 A_raw 평균 micro-F1은 0.593013397, A_old 통발 배수 규칙은 0.574868577, A_micro_select는 0.593352552였다. 새 선택 규칙의 micro 차이는 +0.000339156, paired bootstrap 95% 구간 [−0.000932678,+0.001610989]로 사전 +0.005·양 seed 개선·하한 양수 기준을 통과하지 못했다. 판정 정책을 채택하지 않았고, 모델 실행을 위한 CPU 환경 설치·합성 smoke·입력 계보 감사만 다음 round_004에 넘겼다. (원본: 11_04_final/rounds/round_003/ROUND_REPORT.md)

## round_004 — CPU 환경·개발 입력 준비

TabICL CPU 실행 환경과 개발 입력 문맥을 구성하고 작은 합성 입력에서 실행 가능성을 확인했다. 신규 분류 성능 평가는 하지 않았으며, 16개 합성 FIT+4 query의 4클래스 확률 행합과 반복 추론을 검사했다. RAM 부족 시 처음에는 실행을 보류했고, 사용자의 재확인 지시 후 가용 RAM 4.045 GiB에서 smoke가 13.047초에 exit0으로 끝났다. 체크포인트 110,368,038 bytes의 해시 일치, 계수 27,552,258개, CPU/FP32를 확인했으나 선박 점수나 원 CUDA 재현은 측정하지 않았다. 준비된 원순서 개발 입력을 export하고 두 INNER query를 pilot할 계획이 round_005로 이어졌다. (원본: 11_04_final/rounds/round_004/ROUND_REPORT.md)

## round_005 — 입력 export 성공, 진단 코드 오류로 추론 전 종료

원순서 FIT/INNER 입력이 기준 NPZ와 일치하는지 확인하고 고정 INNER 두 질의를 한 번 추론하려 했다. FIT 3,144×312와 INNER 787×312 float32 배열 export 및 독립 검산은 각각 exit0으로 통과했고, pilot은 24.125초 후 선택 속성 cache_mode_ 접근에서 exit1로 종료했다. predict_proba 호출은 0회라 확률 재현·F1은 산출되지 않았다. 입력 복구만 완료하고 모델 성능 판단은 보류했으며 선택 속성을 안전하게 기록하는 진단 변경을 round_006에 넘겼다. (원본: 11_04_final/rounds/round_005/ROUND_REPORT.md)

## round_006 — 진단 수정 후 실제 추론의 RAM 중단

round_005의 선택 속성 기록 오류를 수정한 뒤 같은 FIT 3,144척과 고정 INNER 2질의의 CPU 추론을 확인했다. mock은 통과했고 pretrained 문맥 fit도 한 번 반환했으나, 실제 확률 계산은 RAM 관문 1.5 GiB 아래로 내려가 27.594초에 소유 프로세스 트리가 중단되어 결과 확률 0개였다. 시작 가용 RAM 4.283 GiB, 최저 1.392 GiB였으며 새 F1·재현 판정은 없다. 이후 동일한 RAM 조건의 재실행을 하지 않고 CPU에서 배치축 분할이 가능한지 합성 비교로 옮겼다. (원본: 11_04_final/rounds/round_006/ROUND_REPORT.md)

## round_007 — 컬럼 분할 경로의 합성 동등성

CPU 추론 경로에서 컬럼 배치축만 chunk16으로 나누어도 확률이 유지되는지 검증했다. 합성 FIT 32×312와 query 2×312, 같은 fitted TabICL estimator에서 원경로와 분할경로의 확률 최대차 0.0, 수치 exact equality 및 두 argmax 일치를 확인했다. 합성 실행은 30.078초, exit0이었고 실제 선박 자료·F1은 0회였다. 작은 입력의 의미 보존을 근거로 같은 어댑터를 실제 FIT/INNER에 적용하는 round_008이 계획됐다. (원본: 11_04_final/rounds/round_007/ROUND_REPORT.md)

## round_008 — 실제 컬럼 분할 추론 중 RAM 중단

합성에서 통과한 COL16 어댑터가 고정 FIT 3,144척·INNER 2 query에서도 확률을 반환하는지 확인하려 했다. 실제 predict_proba는 완료 전 RAM 1.5 GiB 미만에서 25.64초 만에 중단됐고, 첫 컬럼 호출의 14개 chunk만 완료됐다. 최대 관찰 family RSS 3,182,952,448 bytes, 최저 가용 RAM 1.380 GiB였으며 확률·점수는 없다. 전체문맥 재시도는 하지 않았고, ROW 배치축의 분할 가능성을 소스와 합성 입력에서 확인하는 round_009로 바뀌었다. (원본: 11_04_final/rounds/round_008/ROUND_REPORT.md)

## round_009 — ROW 분할의 합성 의미 보존

ROW의 B,T가 독립 배치축이고 ICL은 전체 FIT 문맥을 유지해야 한다는 구조를 작은 합성 비교로 확인했다. 고정 체크포인트를 이용한 합성 입력에서 column16 기준 경로와 column16+row8 경로의 확률 최대차 0.0, exact equality 및 argmax [1,2] 일치를 얻었고 mock·실행 모두 통과했다. 합성 pair 실행은 wrapper 49.187초, exit0이며 실제자료 성능은 측정하지 않았다. 두 어댑터로 고정 실제 두 질의의 유한 재현 1회를 시도하는 계획이 round_010에 반영됐다. (원본: 11_04_final/rounds/round_009/ROUND_REPORT.md)

## round_010 — 실제 두 질의 확률 재현과 소스 동결 위반

COL16+ROW8을 FIT 3,144척과 사전 고정 INNER 2 query에 적용해 저장 확률을 비교했다. 최대절대차는 1.8446231598e-6으로 1e-4 한도를 통과했고 argmax [0,1]도 같았으나, 실행 도중 wrapper가 승인 이후 수정된 사실이 확인돼 전체 출처 gate는 실패했다. Child는 exit0, 확률 계산은 완료했지만 wrapper 종료는 command exit4였으며 새 F1은 없다. 숫자 재현과 실행 출처 유효성을 분리해 보존하고, 모델 재실행 대신 saved output의 provenance 감사와 실행 계약 보강을 round_011에 넘겼다. (원본: 11_04_final/rounds/round_010/ROUND_REPORT.md)

## round_011 — M4 계약 작성, 종료코드 영수증 실패

round_010 저장 결과를 감사하고 M4 합성 head 실험의 수학·데이터 경계를 정하려 했다. 실행기 smoke와 fixture 검사는 시도했으나 fixture 테스트 2개가 OK인 동안 wrapper receipt exit_code=null/completed=false여서 저장 JSON audit은 실행하지 않았다. 모델·학습·새 F1은 0회였고, 두 질의 저장 확률의 과거 산술 검산은 maxabs 1.8446231598e-6이었지만 새 검산 결과가 아니다. exit 코드 회수 경로를 고쳐야 동적 audit을 할 수 있어 해당 수정이 round_012로 이어졌다. (원본: 11_04_final/rounds/round_011/ROUND_REPORT.md)

## round_012 — 실행기 정적 승인 후 시간관문 차단

종료코드를 정수로 회수하고 timeout·프로세스 잔존을 구분하는 실행기 소스를 수정했다. 소스 검토는 승인됐지만 20:42 UTC 실험 cutoff 도달이 runner 실행 전 확인돼 smoke·mock·saved audit·모델 실행은 모두 0회였다. 정적 승인과 동적 성공을 구별했으며 round_010의 수치 재현 기록은 과거 결과로 보존했다. 실행기를 최소 경로로 새 회차에 복사해 동적으로 검증하도록 round_013으로 연결됐다. (원본: 11_04_final/rounds/round_012/ROUND_REPORT.md)

## round_013 — 실행기 동적 확인과 round_010 저장값 감사

종료코드 수집 실행기 smoke, fixture mock 및 round_010 저장 결과 audit을 각각 한 번 수행했다. 세 단계 모두 child/wrapper exit0으로 완료됐고, 저장 JSON에서 2×4 확률 maxabs 1.8446231598e-6, argmax 일치가 재계산됐다. 다만 현재 출처 gate와 round_010 역사 전체 gate는 false였으며, 저장 확률 산술 검산은 새 모델 추론이나 선박 성능 평가가 아니다. 모델을 다시 실행하지 않고 M4 tiny 합성 head 학습·병합·reload 검증을 round_014에 준비했다. (원본: 11_04_final/rounds/round_013/ROUND_REPORT.md)

## round_014 — M4 tiny 합성 코드 동결, 동적 실행 미실시

M4-a/b head-only 학습과 병합, 저장 후 head 재적재를 위한 합성 코드를 작성·검토했다. Python AST와 PowerShell parser 문법 검사만 통과했고, 시간 예산 및 잘못된 승인 hash 때문에 smoke·mock·합성 모델 실행은 전부 0회였다. 실제 계수학습·선박자료·F1 측정도 없다. 새 문서와 실행 코드를 완성했으나 동적 관문을 넘지 못한 상태로 round_015에 이관했다. (원본: 11_04_final/rounds/round_014/ROUND_REPORT.md)

## round_015 — 합성 head 수치 통과, 실행기 판정 실패

M4 head 학습·병합·재적재가 저장 수치에서 정합한지 작은 합성 입력으로 확인했다. seed20261112, context16×8, target4×8, 4-view 조건에서 Python child는 exit0이었고 확률 재구성 최대차 5.9604644775e-8, 초기복사·병합·reload 비교는 0, 지정 gradient·불변성 검사는 통과했다. 하지만 PowerShell이 완료 JSON을 소비할 때 예외를 내고 deadline 이전인데도 timed_out=true를 기록해 전체 execution receipt는 completed=false였다. 모델이나 특징을 재실행하지 않고 JSON·종료 판정 절차를 감사하도록 round_016으로 이어졌다. (원본: 11_04_final/rounds/round_015/ROUND_REPORT.md)

## round_016 — 저장 감사 코드 작성, 승인 전 동적 실행 보류

round_015의 JSON key와 deadline 종료 경계를 모델 없이 확인할 감사 코드를 만들었다. 정적 검사 및 수정은 완료했지만, deadline 후 종료 관측을 정상 종료로 처리할 수 있다는 제어 결함이 남아 독립 승인 없이 smoke·mock·audit을 실행하지 않았다. 실제 학습과 F1은 0회다. 통제 경계 문제를 좁혀 수정한 뒤 같은 저장 증거만 검증하는 계획이 round_017이 됐다. (원본: 11_04_final/rounds/round_016/ROUND_REPORT.md)

## round_017 — PowerShell 불리언 처리에서 smoke 중단

실제 deadline과 OS 종료를 분리하는 제어 코드를 승인·동결하고 smoke를 실행했다. 첫 receipt 작성에서 bareword true가 명령으로 해석돼 exit1이 났고, probe child는 시작되지 않았다. RAM 문제나 모델 결과는 없으며 smoke wrapper 시도만 1회였다. 이 오류는 이전 정적 문법 검사가 의미상 실행 오류를 잡지 못한 사례라 보고서와 소스를 보존하고, 불리언 값을 명시하는 최소 수정을 round_018에 넘겼다. (원본: 11_04_final/rounds/round_017/ROUND_REPORT.md)

## round_018 — 정상 종료 probe 3개 통과, timeout probe 판정 불확정

수정된 receipt 경로와 종료 관찰을 모델 없이 시험했다. 즉시 exit0, exit7, 지연 exit0은 기대대로 분류됐으나 sleep5초/deadline0.5초 probe는 exit code −1 및 유효하지 않은 1601년 시각으로 기록되어 indeterminate 판정에 머물렀다. 네 번째 probe 때문에 전체 smoke는 exit1이었고 auditor·학습·F1은 0회였다. 이번 영수증을 성공으로 고치지 않고 timeout/종료 관찰을 추가 수정하는 round_019로 이어졌다. (원본: 11_04_final/rounds/round_018/ROUND_REPORT.md)

## round_019 — 제어 코드 정적 수정 후 성능 실험 계획으로 이동

round_018의 Wait/deadline 간격을 처리하는 소스를 작성했지만 Python 영수증이 raw ExitTime과 validity 불일치를 걸러내지 못할 가능성을 검토자가 지적했다. 소스 승인 및 동적 검증이 없었고 smoke/mock/audit/model은 모두 0회다. 사용자 우선순위에 따라 다음 두 회차를 성능 비교로 재구성하되, 이 계획만으로 결과를 주장하지 않았다. round_020은 저장된 LGBM·CatBoost·TabICL 확률의 SELECT-only 결합, round_021은 그 stacker에 공간 8열을 추가하는 고정 비교로 넘겼다. ## round_020 — 결합 코드 미완료, 성능 값 없음

저장된 LightGBM·CatBoost·TabICL 확률 12열을 SELECT-only Logistic 결합으로 비교하려 했다. 세 fold의 FIT/ES/SELECT/OUTER 명부와 SELECT 394척의 ID·라벨·확률 정합성은 확인했지만 TabICL loader가 INNER 787행과 SELECT 394행을 잘못 비교하는 오류와 결과 저장·fit 제한 기능이 남아 실행 전 코드 검토를 마치지 못했다. fit 0회, OUTER 평가 0회, 신규 후보 F1 null이라 어떤 방법도 채택되지 않았다. 고정된 next branch의 코드 결함을 고쳐 실제 비교를 한정된 횟수로 수행하는 round_021이 뒤따랐다.
